# mythread 1.7

Это отдельный набор тестов и реализация пользовательских потоков 1.7 в том же
репозитории, что и 1.6. Публичные имена API одинаковы:
`mythread_create`, `mythread_join`, `mythread_detach`, `mythread_exit`.

Общая инфраструктура хранится один раз в `../mythread_tests/`:

- `../mythread_tests/include/` — публичный контракт;
- `../mythread_tests/framework/` — runner и assert-макросы;
- `../mythread_tests/impl/reference/` — pthread reference.

В этом каталоге находятся только отличающиеся части 1.7:

```
mythread_lab_1_7/
├── impl/custom/       # реализация пользовательских потоков
├── tests/             # тесты 1.7, разложенные по темам
├── main.c             # отдельный реестр тестов 1.7
├── Makefile           # подключает общую инфраструктуру 1.6
└── README.md
```

Реализация использует модель 1:m. При первом создании запускается один
служебный pthread, а каждый пользовательский поток получает собственный
`ucontext_t` и стек. Планировщик переключает контексты в кооперативных точках:
при `mythread_join` пользовательский поток блокируется, а возврат из функции
потока завершает его контекст. Вытеснение таймером не используется, что
допускается условием 1.7.

## Сборка и запуск

```sh
make check-custom       # реализация 1.7
make check-reference    # общий pthread reference
make check-strict       # проверки ошибок custom
make check-repeat       # 20 повторов
./mythread_tests 'u17_nested_*'
```

Каталог 1.6 (`../mythread_tests`) сохраняет собственный набор kernel-thread
тестов и свой Makefile. Реестры и тестовые файлы 1.6 и 1.7 раздельны, а общий
код раннера, API и reference не дублируется.

Набор из 16 тестов проверяет создание и возврат значения, `join` с разными
порядками и из пользовательского потока, вложенные цепочки, `mythread_exit`,
detached-жизненный цикл, отдельные стеки, ошибки повторного использования
handle, массовые циклы повторного создания и отсутствие роста числа kernel
threads.
